# ADR-0017: Agent context files

- Status: Accepted (approved by Valery on 2026-10-05)
- Date: 2026-10-05
- Phase: 4
- RFC: [RFC-0001](../../rfcs/0001-ndop-ui.md), "Agent-native DX"
  (project agent context), "CLI" (`ndop init --agent`), Phase 4; ADR-0011

## Context

RFC-0001 has `ndop init` write an `AGENTS.md` section, or `CLAUDE.md`,
`.cursor/rules` or `.github/copilot-instructions.md` depending on
`--agent` (claude-code, cursor, copilot or none), plus a Claude Code skill
at `.claude/skills/ndop/SKILL.md`. `add` (and later `update`) refreshes
them. The content sits between `<!-- ndop:start -->` and
`<!-- ndop:end -->`, so the CLI only rewrites its own section. ADR-0011
deferred all of this, and `--agent`, to Phase 4; no code exists yet.

`ndop.json` has `additionalProperties: false`, so remembering the choice
needs a schema change.

## Decision

### Which files

- `AGENTS.md` is always written, unless `--agent none`: it's the file most
  agents read, and the others point to it.
- `--agent` takes one or more of `claude-code`, `cursor`, `copilot`, or
  `none` (repeatable or comma-separated). Without it, `init` detects:
  `CLAUDE.md` or `.claude/` means claude-code, `.cursor/` means cursor,
  `.github/copilot-instructions.md` means copilot. On a TTY it asks, with
  the detected ones preselected; with `--yes` or `--json` it uses the
  detected ones.
- The choice is stored in `ndop.json` as `agents: string[]`, so `add`
  refreshes the same files. This adds an optional `agents` property to the
  `ndop.json` schema.

| Agent         | Context files                                       | With `--mcp`                        |
| ------------- | --------------------------------------------------- | ----------------------------------- |
| (always)      | `AGENTS.md` section                                 |                                     |
| `claude-code` | `CLAUDE.md` section; `.claude/skills/ndop/SKILL.md` | `ndop` server in `.mcp.json`        |
| `cursor`      | `.cursor/rules/ndop.mdc`                            | `ndop` server in `.cursor/mcp.json` |
| `copilot`     | `.github/copilot-instructions.md` section           | `ndop` server in `.vscode/mcp.json` |

- **MCP registration is opt-in, and an addition to the RFC**, which lists
  context files only. `init --mcp` registers the server for the chosen
  agents; on a TTY without the flag, `init` asks, defaulting to no;
  `--yes` and `--json` never register it without `--mcp`. Each entry runs
  `npx -y @ndop/mcp`, is merged into the existing JSON with the
  JSONC-preserving editor, and never replaces another server. Running
  `init --mcp` again on an initialized project only adds the entries. The
  file names and shapes are checked against each tool's current
  documentation when implemented.
- Whether the server is registered is stored in `ndop.json` as `mcp: true`,
  so the context section either tells the agent which tools to call, or
  how to enable them (`ndop init --mcp`).

### Content

Generated by the CLI from the lock, the registry index and the installed
theme, so it's always true for this project:

- Import aliases (`@/ui/...`, `@/lib/utils`) and where items live.
- Installed items, with versions, as one line each with their selector.
- Token names, grouped, and the rule to use tokens and logical utilities
  (`ms-`, `pe-`) only.
- The rules: prefer an installed component, then `ndop add`, before
  writing new markup; never edit a primitive's internals; read
  `get_component` (or the `.md` twin) before using a component.
- The verify loop: run `ndop verify <paths> --json`, fix every problem,
  repeat until it passes.
- With the MCP server registered, which tools to call and when; without
  it, one line on how to register it.

`CLAUDE.md`, the Copilot file and the Cursor rule carry the same section.
`SKILL.md` has front matter (`name: ndop`, a `description` saying when to
use it) and the same guidance, ordered as a workflow. The section stays
under about 80 lines so it doesn't crowd the user's own instructions; the
component details stay behind `get_component`.

### Writing

- Files go through the plan (`PlanBuilder`), so `--dry-run` shows their
  diffs and `--json` lists them, like every other file.
- In a shared file, only the text between the markers is replaced. With no
  markers, the section is appended after a blank line; a missing file is
  created. Text outside the markers is never touched, and a file with
  unbalanced markers is skipped with a warning naming it.
- Files Ndop owns outright (`SKILL.md`, `ndop.mdc`) are rewritten whole,
  but skipped with a warning if their hash differs from the last one
  written. Those hashes go in the lock under a new `agentFiles` map, so the
  lock schema gains an optional property.
- Agent files are not registry items: their template ships with the CLI
  and versions with it.
- `add` refreshes the section after installing items. A run that changes
  nothing leaves the files byte-identical, which keeps `add` idempotent.

## Consequences

- An agent opening the project learns what's installed and how to verify,
  without the MCP server.
- `ndop.json` and the lock gain optional properties; existing files stay
  valid.
- The registry install test (ADR-0015) checks that `init` writes the
  files, that a second `add` leaves them unchanged, and that text outside
  the markers survives.
